# OnePlus Ace 3 Pro (PJX110 / corvette) 适配说明

面向 ColorOS 14（Android 14）原厂内核 `6.1.57-android14-11-o-gfc2eac419e6e`。
目标是让 Droidspaces 在这台机器上跑起来，**不刷内核、不动 vendor_boot、不碰厂商模块**。

## 1. 这台机器的状况

| 项目 | 值 |
| --- | --- |
| 型号 / 代号 | PJX110 / corvette |
| 平台 | SM8650-AB（骁龙 8 Gen 3），4 KiB 页，arm64 |
| 出厂系统 | ColorOS 14，Android 14（API 34） |
| 内核 | `6.1.57-android14-11-o-gfc2eac419e6e` |
| KMI | `android14-6.1` |

`-o-` 是 OPlus 私有改动标记。OPlus 在 ACK 基线上加了调度、内存、温控模块，
但对外仍然遵守 android14-6.1 的 KMI，所以厂商的 200 多个 `.ko` 才能和 GKI 内核互相加载。

这台机器上**不要**走"重编内核 + 打 kABI 补丁"那条路：OPlus 的模块（`oplus_bsp_sched_assist`、
`oplus_bsp_task_sched` 等）没有源码，重编内核后 MODVERSIONS 的 CRC 一变，整机起不来。
这正是 Droidspaces 官方文档里 [GKI 章节](../..) 警告的 `CONFIG_SYSVIPC` 场景。

## 2. 原厂内核缺什么

`android14-6.1` 的 GKI 配置里，Droidspaces 需要的这几项是关的：

| 配置 | GKI android14-6.1 | Droidspaces 需要它做什么 | 缺了会怎样 |
| --- | --- | --- | --- |
| `CONFIG_PID_NS` | 关 | PID namespace | **容器起不来** |
| `CONFIG_SYSVIPC` | 关 | SysV 消息队列/信号量/共享内存 | **容器起不来** |
| `CONFIG_DEVTMPFS` | 关 | 内核直接提供 `/dev` | 硬件访问受限（Android 用 tmpfs + ueventd 顶） |
| `CONFIG_USER_NS` | 关 | Sandboxing（`--allow-sandboxing`） | 沙箱功能不可用 |
| `CONFIG_CGROUP_DEVICE` | 关 | 设备 cgroup 白名单 | 设备隔离退化 |

已经在的，不用管：`CONFIG_IPC_NS`、`CONFIG_POSIX_MQUEUE`、`CONFIG_NET_NS`、`CONFIG_VETH`、
`CONFIG_BRIDGE`、`CONFIG_OVERLAY_FS`、`CONFIG_FUSE_FS`、`CONFIG_TUN`、`CONFIG_MACVLAN`。

本模块就地补上前两项（PID / IPC namespace，含 SysV IPC 与 POSIX mqueue）。
devtmpfs 与 user namespace 属于 `src/misc/`，上游目前只在 6.6 / 6.12 上开，
6.1 分支没有产出，所以这台机器上 `droidspaces check` 的 devtmpfs / Sandboxing 会是黄的，不影响起容器。

## 3. 为什么必须按 `uname -r` 编

`insmod` 时内核会把模块里的 `vermagic` 和运行中内核的 `vermagic` **逐字节**比较，
不相等就 `-ENOEXEC`，用户态看到的是：

```
insmod: failed to load ...: Invalid argument   (dmesg: version magic '6.1.166-dirty ...' should be '6.1.57-android14-11-o-gfc2eac419e6e ...')
```

DDK 自带的 kdir 是 `6.1.166-dirty`，直接用 `make VER=android14-6.1` 编出来的 ko 在任何原厂
6.1.57 上都装不上。`scripts/build-device.sh` 的做法是：把 kdir 复制一份，只改
`include/generated/utsrelease.h` 里的 `UTS_RELEASE`，再编译。符号表、CRC、段布局全都不动，
所以模块仍然靠运行时的 `kallsyms` 解析符号（`__versions` 是空的），跨 minor 版本也不会因为 CRC 被拒。

`SMP preempt mod_unload modversions aarch64` 这一段来自内核 `.config`，OPlus 6.1 和 GKI 一致。
真机上一旦发现对不上（极少数 OTA 会关 PREEMPT），先跑 `scripts/collect-device.sh` 把
厂商 `.ko` 里的 `vermagic=` 抓出来，再决定要不要改 kdir 配置。

OTA 之后 release 里的 hash 会变，**每次系统更新都要重编一次**，否则装上去就是不生效。
安装脚本会读 `kernels/<kmi>/vermagic.txt` 和 `uname -r` 比对，不一致会在安装日志里直接喊出来。

## 4. 构建

本机需要 Docker：

```sh
# 用 devices/pjx110.conf 里的 known_release
scripts/build-device.sh android14-6.1

# 或者按真机 uname -r 指定
scripts/build-device.sh android14-6.1 6.1.75-android14-11-o-g1234567890ab
```

CI 走 `.github/workflows/device.yml`：Actions → Build device module → Run workflow，
填 `kernel_release`，产物是 `droid_lkm.ko` + 安装 zip。

依赖由 KMSDK 拉取（`deps.lst` 固定 rev），首次需要联网：

```sh
scripts/fetch-deps.sh
```

## 5. 安装

1. 确认 root 方案支持 insmod：KernelSU（含 Next / SukiSU / ReSukiSU）或 APatch。
   Magisk 也行，走 `/data/adb/magisk/busybox insmod`。
2. KernelSU 管理器里安装 `phDroid-<version>.zip`，**不要**点"立即重启"，先看安装日志末尾的
   `kmi` / `vermagic` 两行。
3. 重启。模块在 `service.sh`（late_start）阶段加载，日志在
   `/data/adb/modules/phdroid/phdroid.log`。
4. 装上 Droidspaces，跑：

```sh
su -c droidspaces check
```

期望：PID / MNT / UTS / IPC namespace 全绿，`devtmpfs`、`Sandboxing` 黄（原因见第 2 节）。

### config.conf 关键项

装完在 `/data/adb/modules/phdroid/config.conf`，改完重启生效：

| 键 | PJX110 建议 | 说明 |
| --- | --- | --- |
| `kmi` | `android14-6.1` | 安装时自动写入，不要手改 |
| `compat` | `off` | 6.1 不产出 `droid_lkm_vendor.ko`，开了也没东西可加载 |
| `selinux_fix` | `1` | OPlus 策略默认拒绝 su 域的 `module_load`，让脚本自己补一条最小规则 |
| `inline_hook` | `1` | PID/IPC 入口替换靠 inline hook，关掉就只剩符号替换 |
| `verbose` | `0` | 排障时改 1，会把每个 hook 入口打出来，日志量很大 |
| `gate` | `0` | ≥1 时先做一次预检再激活，起不来时改 1 定位 |

## 6. 排障对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `version magic ... should be ...` | ko 和本机 release 不一致 | 按本机 `uname -r` 重编，见第 3 节 |
| `Key was rejected by service` | 内核开了 `MODULE_SIG_FORCE` | 原厂一般不开；真开了只能走内核补丁，本方案不适用 |
| `Operation not permitted` | SELinux 拦了 `module_load` | `selinux_fix=1`；还不行就用 magiskpolicy 手工补 `allow su <ko 的 type>:system module_load` |
| 加载成功但 `droidspaces check` 还是红 | `droid_lkm` 没真正激活 | `cat /sys/module/droid_lkm/parameters/*`，`verbose=1` 重启再看 dmesg |
| 开机卡住/重启循环 | insmod 中途崩 | 脚本会写 `insmod.crash` + `blocked`，下次开机不再加载；删掉 `/data/adb/modules/phdroid/blocked` 才会重试 |
| 容器能起，Docker 报 device cgroup | `CONFIG_CGROUP_DEVICE` 关 | 容器内 Docker 用 `--cgroupfs`，或接受限制 |

## 7. 风险与回滚

- 模块 patch 的是 `copy_process` / `do_exit` / `sys_call_table` 这些核心路径，出问题表现是**重启**，
  不是报错。第一次装之前把 `boot.img` 留着，心里有数就行——本方案不碰任何分区，删模块即恢复。
- 卸载：管理器里禁用模块 → 重启。已激活的模块**不能热卸载**，必须重启。
- `/sys/fs/pstore/` 里能捞到重启前的日志。

## 8. 还没做的

- `src/misc/` 的 devtmpfs、user namespace、netfilter 扩展在 6.1 上没有产出（上游在 6.6/6.12 上做）。
  要把 PJX110 的 `droidspaces check` 全绿，得先把这几块移植到 6.1。
- `--cpus` / `--pids-limit` 依赖 `CONFIG_CFS_BANDWIDTH` / `CONFIG_CGROUP_PIDS`，这两个会改
  调度器和 cgroup 结构体大小，kABI 直接崩，**GKI 上不能用**，容器限额里这两项会灰掉。
- 没做真机验证：本仓库没有 PJX110 的测试记录，第一次加载请当作实验。
